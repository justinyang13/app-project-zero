# 14 — Persistence & Saves

## 1. Storage backend

IndexedDB (via the `idb` library, see
[01 — Tech Stack & Architecture](01-tech-stack-architecture.md) §1) is the
sole persistence layer — no backend, no account, no cloud sync in the
MVP (see [00 — Vision & Scope](00-vision-and-scope.md) §4). IndexedDB is
chosen over `localStorage` specifically because: it supports storing
binary `ArrayBuffer`/typed-array data natively (chunk block data is
exactly this), it has a far higher storage quota (browser-dependent, but
typically hundreds of MB to several GB, vs. `localStorage`'s ~5–10MB),
and reads/writes are asynchronous (won't block the main thread the way
synchronous `localStorage` access would during an autosave).

## 2. What gets persisted, and what doesn't

- **Persisted per world:** every chunk that has ever been *modified* from
  its generated state (see below), all entity state (player inventory/
  stats/position, tamed creatures, dropped items with pending despawn
  timers), world metadata (seed, world type, difficulty, game mode,
  worldTime, weather state, spawn point), and the player's Blueprint
  Library (shared across all worlds, not per-world — see
  [06 — Building Tools](06-building-tools.md) §2.4).
- **Not persisted — regenerated on demand:** any chunk that has *never*
  been modified from its as-generated state is not stored at all; it's
  simply regenerated by the deterministic pipeline (see
  [02 — World Generation](02-world-generation.md) §1 and
  [01](01-tech-stack-architecture.md) §9) the next time it's loaded. This
  is the single biggest space-saving decision in the persistence model —
  an explored-but-untouched world of any size costs close to nothing to
  save, only *edits* have a storage cost.
- **Chunk diff format:** a modified chunk is stored as a sparse list of
  `(localBlockIndex, blockId)` overrides rather than a full re-serialized
  32×32×32 block array, unless the fraction of modified voxels in that
  chunk exceeds a threshold (~40%), at which point it's cheaper to store
  the full block array directly (an automatic per-chunk choice made at
  save time, transparent to the loader). Light data is never persisted —
  it's always recomputed from block data on chunk load (cheap relative to
  generation itself, and avoids storing redundant derived data).

## 3. Autosave & explicit save

- **Autosave** runs on a timer (default every 2 real-world minutes) and
  on specific trigger events (closing the tab via `beforeunload` — a
  best-effort synchronous-as-possible flush, opening the Pause menu,
  sleeping in a bed). Autosave only writes chunks/entities that are
  actually dirty since the last save (a per-chunk dirty flag set on any
  block edit or significant entity state change), keeping routine
  autosaves fast even in a large, heavily-built world.
- **Explicit save** (the Pause menu's "Save Now" button, see
  [12 — UI/UX](12-ui-ux.md) §7) forces an immediate full dirty-flush
  regardless of the autosave timer, with a brief non-blocking "Saving…"
  toast confirmation.
- Saves never block gameplay — the actual IndexedDB write happens off the
  critical path (batched, async), with the simulation continuing to tick
  during a save (unlike the Pause-menu-triggered save, which happens
  while the game is already paused for other reasons).

## 4. World save structure (IndexedDB schema)

Object stores (see [23 — Data Schema Reference](23-data-schema-reference.md)
§8 for full TypeScript interfaces):

- `worlds` — one record per world: id, name, seed, worldType, gameMode,
  difficulty, createdAt, lastPlayedAt, playTimeSeconds, thumbnail (small
  base64/blob PNG).
- `worldState:{worldId}` — one record: worldTime, weather, player state
  (position, rotation, health, hunger, stamina, inventory, armor,
  spawn point), entity list (tamed/named creatures, dropped items with
  despawn timestamps).
- `chunks:{worldId}` — keyed by chunk coordinate string, one record per
  *modified* chunk holding its diff or full block array (§2) plus a
  schema-version tag (§5).
- `blueprints` — global, not per-world: id, name, thumbnail, block-list
  data (see [06](06-building-tools.md) §2.4), createdAt.
- `settings` — global: video/audio/controls/accessibility/gameplay
  settings (see [12](12-ui-ux.md) §9), not tied to any world.

## 5. Versioning & migration

Every persisted record (world metadata, chunk diff, blueprint) carries a
`schemaVersion` integer. On load, if a record's version is older than the
current app's expected version, a migration function chain (one function
per version bump, each transforming `vN → vN+1`) runs before the data is
used — keeping migrations small, linear, and independently testable
rather than one large branching function. World-generation pipeline
changes (new biomes, tuning changes — see
[02 — World Generation](02-world-generation.md) §8's note on this) do
*not* require chunk migration, since only already-generated (and
therefore already-stored) chunks are affected by old logic, and those are
stored as concrete block data, not regenerated from the new pipeline —
the seed's *new* unexplored territory simply uses the new pipeline
naturally, which is the expected, desired behavior (matches how the
genre baseline itself handles version updates to terrain generation).

## 6. Export / import

- **World export:** serializes an entire world record (metadata + all
  entity state + all modified chunks) into a single downloadable file
  (`.simcraft` extension, actually a gzip-compressed JSON+binary
  container — binary chunk arrays base64-encoded within it, or packed via
  a lightweight custom binary framing if profiling shows base64 overhead
  matters at realistic save sizes) via the browser's native file-download
  mechanism. This is the supported way to back up a world outside the
  browser's storage, move it to another device/browser, or (informally)
  share a build with someone else.
- **World import:** a file picker on the World Select screen (see
  [12](12-ui-ux.md) §2) reads a `.simcraft` file, validates its
  schemaVersion (running migration if needed, per §5), assigns it a new
  local world id (never silently overwrites an existing save with a
  matching name — always creates alongside, renaming if a collision
  exists), and adds it to the world list.
- **Blueprint export/import:** same mechanism, scoped to a single
  Blueprint record (see [06](06-building-tools.md) §2.4), producing a
  much smaller `.json` file suitable for casually sharing one structure
  rather than a whole world.

## 7. Storage quota & resilience

- The Settings → Storage panel (see [12](12-ui-ux.md) §9) surfaces
  current IndexedDB usage (via `navigator.storage.estimate()` where
  available) so a player can see how much space their worlds are using
  and proactively export/delete old saves.
- `navigator.storage.persist()` is requested on first world creation
  (with graceful no-op if denied/unsupported) to reduce the chance the
  browser evicts SimCraft's data under storage pressure — the practical
  risk this mitigates for a game with no cloud backup.
- If an IndexedDB write fails (quota exceeded, browser storage disabled
  in a private/incognito context, etc.), the game surfaces a clear,
  non-silent warning ("This world could not be saved — your browser's
  storage may be full or disabled") rather than failing silently and
  losing progress without the player knowing.
